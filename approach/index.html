Start from the goal

Sam Beckwith III · AI Platform Engineer and Senior SRE · October 2026

I start every AI project with two questions. How can a team use AI to accomplish more, at higher quality, without our costs growing as fast as our output? And how should engineering, customer service, research, finance, and other roles work once agents can take on whole tasks?

I don't see AI as a way to make today's process a little faster. I see it as a drastic change in how the work gets done, for engineering and for every other role where the result can be checked.

With AI agents, the prompts matter less than the system around them: which step each agent owns, how the work gets checked, and when a person decides. That system is what I design and build.

A common way to run a coding agent is to give it a goal and let it retry until it decides the goal is met. That works for small tasks. On larger work it breaks down. Each retry patches the last attempt, and nothing outside the agent checks the result.

So I design backwards from the result. I start with what has to be true when the work is done, then decide which checks prove it. These are the design choices behind the systems on this site:

  • Work starts from requirements and a design. Critic agents debate and vet both before any implementation begins.
  • Models do the non-deterministic work, such as implementing code, reconfiguring a service, examining data, and drafting communication. Code does the deterministic work: the workflow itself, the tests and analysis tools, and measuring how each model performs.
  • When tests or review agents fail, the pipeline feeds the failure back to the agents, and they revise. This repeats within set limits until the work meets the requirements and fits the design. If progress stops first, a person decides the path forward. A person always does the final review.
  • Each piece of work lives in a CTX project, from my open-source pi-toolbag. A run can cross several hundred context compactions yet the agent stays on point. Work can fan out across many agents, and all of them stay focused on the same goal.
  • My investigation pipeline posts a quick report on the likely cause of an issue, then runs a deeper investigation that doesn't assume the quick report is right. It checks source code, including third-party code, plus documentation, logs, events, and traces.
  • Agents run in a sandbox with read-only access to cloud infrastructure and clusters. They act through outputs a person reviews: pull requests, helper scripts, and reports.
  • In my garage assistant, three vision models read each receipt and vote on each field, so one model's misread doesn't get through.
  • When a model fails, the request moves to the next model in the chain.

Speed only helps if the team can trust the output. Agents also review designs, documents, and planned changes, and they flag security vulnerabilities before release.

The result is a different split of the work. Agents do the implementation, the investigation, and the routine parts of documentation and project tracking. People set the goals, make the design decisions, and approve what goes out. I think the same split applies to customer service, research, and finance, wherever the result can be checked.
