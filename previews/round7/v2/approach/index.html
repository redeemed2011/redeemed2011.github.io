Start from the goal

Sam Beckwith III · Senior Site Reliability Engineer & AI Engineer · October 2026

Agent loops like /goal and Ralph are popular right now, and they're useful. You give an agent a target, and it keeps trying until the target looks met. For many tasks, that is enough. But it's still a vibe loop. The agent usually decides when it's done, and each pass patches the last one, so the result is only as good as that loop happens to get.

I want results my team can rely on, at the same quality on Monday as on Friday. To get there, I stopped asking how to make the last attempt a little better and started asking what it takes to reach the result I want.

Nobody reached space by asking how to make a plane fly higher. They asked how to get to the moon, and that question needed a new kind of machine.

My moon is 100x the quality and output from an engineering team without 100x the cost. Hiring more people won't reach that, and neither will doing the old process faster. It takes a new way of working, designed backward from the goal.

Here's what that looks like in practice. Work now starts in a CTX project, my default for many months. It holds the work's definition, evidence, and decisions, and it generates a spec or an architecture decision record (ADR) where that helps the project. I've moved off spec-driven development. Deterministic code runs the steps that must come out the same every time, and LLM agents handle the steps that need judgment. The workflow tests its own work, critic agents review it, and it fixes the gaps it finds before it opens a pull request. My team relies on my PR review pipeline for its review feedback. My investigations pipeline gives a quick report on the likely cause of an issue, then runs a thorough investigation that doesn't assume the quick answer is right. In my garage assistant, several models read each receipt and vote on each field, so one model's misread doesn't get through. Agents work in a sandbox with read-only access to cloud infrastructure and clusters, so many can run at once and none can change production by accident. When a model fails, the request goes to the next model in the chain.

Speed only matters if I can trust the result. So I build agents I can trust. They write code, configuration, and web designs better than most engineers. They review and critique work, find security vulnerabilities, and give useful feedback on reports, designs, documents, messages, and planned changes before they release. Trust is what lets me hand agents real work, and handing them real work is how a team beats its competition.

I want people out of the loop everywhere the human touch isn't needed: code, web design, documentation, email, CRM, project management, and the rest. Agents do the routine work. People make the calls that need judgment and approve what goes out. My team gets back the hours it spent on toil and puts them into work that needs a person.

The prompts matter less than the system around them: which step each agent owns, how the work gets checked, and when a person decides. Get that right, and people can stop checking every step and spend their time on the bigger picture.
