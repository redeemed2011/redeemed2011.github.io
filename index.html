>AI Delivery Pipeline · 2025–present

Agent pipeline that turns tickets into reviewed pull requests

Agents take a ticket from requirements to a reviewed pull request. A person steps in for final review, or when the work stops making progress.

The hard part is getting model output to a state a reviewer can trust. So plain code runs the steps that must be the same every time, and models run only the steps that need implementation and judgment.

>run ticket-to-pr

  1. 01Ticket
  2. 02Design and requirements
  3. 03Critic agents vet the design
  4. 04Implementation
  5. 05Tests and analysis
  6. 06Review agents
  7. 07Revise until it passes
  8. 08Pull request for final review

How it works

  • From the ticket, agents write the design and requirements. Critic agents debate and vet both before any code is written.
  • Agents implement the changes the requirements call for, within the design. The work then goes through rounds of review and revision until it meets the requirements and fits the design.
  • When tests or review agents fail, the pipeline loops back to implementation for as long as each pass makes progress. When progress stops, it halts and brings in a person to decide the path forward.
  • Models do the non-deterministic work, such as implementing code, reconfiguring a service, examining data, and drafting communication. Code runs the workflow, the tests and analysis tools, and the measurements of each model's performance.
  • The same pipeline runs investigations and research, started by an event, a ticket, or a prompt.

Why it matters

  • Engineers review finished, tested changes instead of writing routine ones, so their time goes to design and final approval.
  • A person is needed at two points: final review, and when the work stops making progress. The rest runs without waiting on anyone.
  • Feature code, on-call work, internal tooling, investigations, and research all run through one pipeline, so the team hands agents whole kinds of work instead of single prompts.

>AI Infrastructure · 2024–present

AI agents for code review, incident investigation, and infrastructure work

Agents investigate incidents, review code, and prepare infrastructure changes. They cut mean time to recovery (MTTR) and tripled my output over the last year.

  • 3x over the last year

These agents work against production systems, so the access model came first. A container sandbox gives them read-only access to cloud infrastructure and Kubernetes clusters. They act only through outputs a person reviews: pull requests, helper scripts that let a person make a remote change quickly, and reports.

What I built

  • An AI pull request review pipeline that my team uses for review feedback.
  • An incident investigation pipeline. It posts a quick report on the likely cause, then runs a deeper investigation that doesn't assume the quick report is right. The deeper pass uses every relevant source it can reach, including source code (even for third-party services involved), documentation, logs, events, and traces. It suggests fixes when asked.
  • The specialist and critic agent roles, their prompts, and the orchestration that passes work between them.
  • One workflow run can cross many context compactions, when the agent trims its history to fit the model's limit. The agent keeps its goal through all of them because it works from a CTX project, from my open-source pi-toolbag. My sessions regularly pass several hundred compactions with no sign of the agent losing track.
  • An agent finishes the top-priority or selected item, then picks up the next. Research, investigation, and evidence gathering fan out across many agents in parallel, and all of them stay focused on the same goal.

Why it matters

  • Engineers start each incident with a likely cause, then get an answer that has been checked against the code, logs, and traces.
  • Agents now do work that used to wait for a person, such as review and root-cause analysis, which is how my output tripled in a year.
  • Agents can't change live infrastructure, and their work is checked before anyone acts on it, so the team trusts them with more of its work.
  • I've taught my team and other engineers to use this tooling, so the new way of working spreads beyond my own work.

Self-service infrastructure-as-code platform

254 engineers make their own infrastructure changes, and policy checks run on every change before it reaches production.

What I built

Why it matters

>Garage Assistant · 2026 · Slack, web board, Cloudflare

AI garage operations assistant and build tracker

For a vehicle build and repair shop, it replaces a spreadsheet, a whiteboard, a retyped daily status doc, and a group text.

The design goal was to keep the crew's habits. Mechanics keep posting from their phones in Slack, and the assistant does the filing.

How it works

  • The build crew posts texts, photos, receipts, PDFs, and voice notes in Slack, and the assistant files each one to the right build. When the build is unclear or a post looks like a duplicate, it asks instead of guessing.
  • Three vision models read each receipt in parallel, a majority vote decides each field, and the assistant checks the arithmetic.
  • Corrections work in plain words, such as "move the water pump to the other truck".
  • The garage manager gets a daily labor report and a phone-first board by build stage, with tasks, parts, receipts, and photos for each build.
  • Every change is logged and can be undone, and nothing is hard-deleted. Invoiced records stay locked to their build.
  • A watchdog resends any post that stalls, then alerts a person. Failed deploys roll back on their own, nightly backups get a monthly restore drill, and about 50 Cucumber feature files gate every release.

Why it matters

  • Every build keeps a complete record, and the mechanics didn't have to change how they work.
  • Nobody retypes the day's status. The garage manager sees every build on a phone.
  • Mismatched totals, duplicate invoices, and unusual prices are caught and sent to a person.
  • The whole system runs on Cloudflare's $5-a-month Workers plan.

>pi-toolbag · 2026 · open source · github.com/redeemed2011/pi-toolbag

pi-toolbag: context recovery and model failover for coding agents

Coding agents keep their goal through several hundred compactions and switch models when a provider fails.

Open-source TypeScript extensions for the Pi coding agent.

How it works

  • When the agent compacts (trims) its history to fit the model's limit, CTX rebuilds its working context from typed records, within a fixed token budget and with no extra model call.
  • A shared failover library replays a failed request on the next model. It switches after a quota error, a timeout, a provider safety error, or a stalled stream. It never switches on an auth error or a refusal.
  • It switches away from a model before the model hits its usage cap, and back once usage recovers.
  • An agent's notes become project rules for later sessions only after a person confirms them.

Why it matters

  • Long tasks can run for as long as they need. After each compaction, the agent picks up where it left off.
  • A provider outage doesn't stop the work. The agent moves to the next model and keeps going.

  • Pi coding agent
  • Vitest
